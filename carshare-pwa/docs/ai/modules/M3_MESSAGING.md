# Module 3 — Messaging

## Owner
Chong Zheng Zhe

## Purpose
Supabase-backed Ride and friend communication for UC3.4, UC3.7, and UC3.8.

## Implemented Contract

- Phone list/conversation navigation remains split while layouts above 900 px use
  a two-column conversation-list + chat surface. Private and group conversation
  details use the same three-dot `Conversation details and management` action on
  every viewport. The shared adaptive dialog is a scrollable bottom sheet on
  phone and a centred dialog on larger screens, showing live route, lifecycle,
  schedule, roles, and members. The desktop trip-details sidebar is not rendered.
- A signed-in non-Host can create or reuse one direct chat for a Published ride from Ride Detail; acceptance is not required.
- Accepting the first ride request creates the ride's one group chat in the same transaction and adds the Host plus accepted account holder. Later accepted account holders join that group. Companion names never become members.
- Friendships require a request and explicit acceptance. Each canonical account
  pair owns at most one permanent `friend`-scoped direct conversation, created
  in the acceptance transaction and kept separate from every Ride direct/group
  conversation. Removing a friend keeps that chat in Messages as read-only;
  accepting a later request reuses its conversation ID and visible history.
- `/message/friends` lists Incoming requests, Friends, and Sent requests. There
  is no global member search: discovery comes from `/users/:userId` and an
  owner-shareable public profile link. Friend requests appear at the Friends
  entry and in the shared notification centre, never in the Message unread sum.
- A normal user message is one atomic bundle containing any non-empty combination of up to 1,000 text characters, 10 mixed images/videos, and one current GPS location.
- Images: JPEG/PNG/WebP, 10 MB each. Videos: MP4/WebM/QuickTime, 50 MB each. Combined media: 100 MB per message.
- The composer camera action sits beside the file action. It opens a bottom sheet on mobile and an anchored menu on desktop. On mobile, `Take photo` delegates to the operating-system camera through a capture-enabled file input; on desktop, it uses an in-page HTTPS `getUserMedia` preview and captures a JPEG frame. `Record video` stays inside the HTTPS page and uses `getUserMedia` plus `MediaRecorder`; mobile users choose either the front or main (rear) camera before recording, while desktop goes straight to its available front camera. It prefers H.264/AAC MP4 for cross-device playback and falls back to WebM only where necessary, then adds the stopped recording to the existing media draft. The normal file action remains the fallback for unsupported browsers.
- A voice message is a standalone 1-180 second audio attachment limited to 10 MB. Browser `MediaRecorder` manages the recording lifecycle while Web Audio captures a 16 kHz mono PCM WAV playback-safe fallback (about 5.8 MB at three minutes) for Chromium/Electron environments whose WebM output lacks usable media metadata. WebM, MP4, Ogg, and WAV are accepted. Recording is stopped automatically at three minutes; stopped recordings remain as in-memory drafts for preview, retry, or deletion.
- Active direct and group chats support WebRTC voice calls on phone and desktop browsers. A group caller selects which members to ring; unselected members receive no call participant row or push. Group calls use a peer mesh capped at eight active members; every invitee can answer or reject independently, joined members connect to each other, and one member leaving does not end a call while at least two accepted members remain. A recipient can answer or reject a global incoming-call prompt from any authenticated route; connecting, connected, and reconnecting calls expose one icon-only minimize action and a non-modal floating bar with participant, status/duration, mute, expand, and end while the user navigates other app routes. The full call view and floating bar contain no separate browse menu. The route-external `CallSessionProvider` keeps the WebRTC session alive. Calls request audio only, release every media track on exit/failure, time out each unanswered invitation after 45 seconds, end at 60 minutes, and provide a manual playback action when browser autoplay policy blocks remote audio. Incoming-call state bypasses the PWA data cache and is rechecked after Realtime subscribes/reconnects, browser focus, visibility restoration, and network recovery. Opted-in devices receive a Push-only 45-second incoming-call alert that opens the conversation and carries the exact call ID; an already-open call client is focused and resynced without a destructive page reload. Local Vite development unregisters production workers/caches from the same origin so two Chrome profiles cannot remain on different bundles. Cloudflare TURN credentials are issued per participant for 75 minutes by an authenticated Edge Function; an unavailable/stale/900 GB-blocked relay degrades to STUN-only with an in-call warning.
- The full group-call surface shows every invited participant in one horizontal row. Accepted members have a labelled green presence light; ringing and terminal per-member states remain visible with text. Phones scroll the row horizontally instead of shrinking or wrapping avatars. While connected, local Web Audio analysis identifies simultaneous speakers without transmitting extra data: a speaking member receives a labelled green ring and waveform badge, with static emphasis under reduced-motion preferences. Analysis nodes and timers follow the existing call-stream cleanup lifecycle.
- Call presence is device-bound and refreshed every 20 seconds. Migration `077` releases a call interrupted by a refresh on the same tab and expires `accepted` rows after 90 seconds without either participant heartbeat, preventing an orphaned database row from reporting that a user is still on another call. A separate tab/device with a live heartbeat remains protected.
- Outgoing, connecting, connected, and reconnecting calls can be minimized without ending WebRTC. The full call surface and global mini bar provide direct Chat, current Ride/Rides, Trips, and participant Profile navigation so users can inspect trip information while audio continues.
- Received text messages can be translated on demand, and either member's standalone voice message can be transcribed then translated, between English, Simplified Chinese, Bahasa Melayu, and Tamil. The last target language is remembered locally per account. Results are shared and source-versioned in Supabase so repeated requests do not spend the free Cloudflare allowance again.
- Translation uses the authenticated `m3-message-translation` Edge Function. SEA-LION performs language detection and translation; Whisper Large V3 Turbo transcribes private voice audio. Cloudflare credentials remain server-only. Reading a translated result aloud is an independent, user-triggered browser `speechSynthesis` action and is disabled when the device has no matching voice.
- Rendering order for normal bundles is text, ordered media grid, then Google Maps Embed `place` mode. Location is coordinates only; no geocoding. Voice messages render with native audio controls and use `Voice message` in list/history summaries.
- Message and call avatars use the current profile URL when it loads; failed or unavailable external avatar images fall back to the participant's initials instead of leaving a broken image.
- A direct-chat participant's avatar and name link to Module 1's privacy-filtered `/users/:userId` profile. Group headers remain group-level and do not imply a single profile owner.
- The original sender can atomically edit a complete normal bundle only before another member reads it. Voice messages cannot be edited. Every member can delete individual messages and call timeline records for their own account, including received messages and shared tombstones. Personal deletion persists across devices without removing shared media or disrupting call signalling. The original sender can delete any user message (including voice and Ride invitations) for everyone only while unread by every other member and while the conversation permits interaction. Shared deletion leaves a tombstone. Migrations `089` and `090` enforce these rules in the database.
- History is oldest-to-newest and searches text, system messages, and media filenames. Results safely highlight the keyword and jump back to the original message.
- Archive, unarchive, delete-for-me, mute, and unmute are personal controls for both direct and group Ride conversations only when the Ride is Completed, Cancelled, or Expired; friend conversations allow them at any time. Archive moves a conversation into the small archive-icon list and remains reversible; a new message restores archived current members to Active. Delete-for-me hides only that member's current history/list row; a later message can resurface the conversation with only post-delete history. Muting preserves message delivery and unread counts while suppressing its message notification and Push.
- Completed, Cancelled, and Expired rides retain direct and group conversations for seven days, then RLS removes all access and the client evicts expired list/detail caches. Completed groups remain writable; Cancelled and Expired groups are read-only. Direct chats remain writable and callable during retention.
- A requester who cancels an Accepted request immediately disappears from the current group member list. Their conversation stays in Active for seven days with read-only access only to messages/calls created before cancellation; they receive no later group messages. Re-acceptance restores current membership and the same Ride history. Manual Leave Group is removed, and the earliest personal-cancellation or Ride-terminal deadline wins.
- Active-conversation unread totals appear on the shared Message navigation item. New Realtime notification inserts play one browser-generated bell when the account-local `Alert sounds` preference is enabled; `voice_call` inserts skip that bell because incoming ringing calls use a separate repeating two-pulse ringtone. Sound stops on every call exit state. Autoplay-blocked clients retain visual, vibration, and Push fallback and expose an enable-sound action. A background/closed PWA uses only the operating-system notification sound because Web Push cannot select this custom Web Audio ringtone. Clicking Message or call Push navigates an existing or newly opened PWA window directly to `/message/:conversationId`; `postMessage` is only the compatibility fallback.
- `call_sessions` rows merge with ordinary messages by creation time in the conversation timeline. Entries show local incoming/outgoing direction, terminal result, start time, and connected duration without counting as unread or moving the message read cursor. No call audio is recorded or uploaded.

## Architecture

- Presentation: `src/presentation/components/messaging/` and routes `/message`, `/message/friends`, `/message/:conversationId`, `/message/:conversationId/history`. `useVideoRecorder.js` owns in-page camera permission, supported MP4/WebM selection, the 50 MB stop guard, and camera-track cleanup.
- Business logic: `src/business-logic/MessagingService.js` validates bundles, standalone voice messages, Ride/friend conversation states, and the four translation targets; `FriendshipService.js` owns relationship mapping and transitions. Messaging coordinates uploads and translation requests, maps `messageTypes`, and keeps failed drafts retryable. `src/business-logic/AlertSoundService.js` uses browser Web Audio for the notification bell and ringtone without audio assets or paid services. `src/presentation/components/messaging/useVoiceRecorder.js` owns voice-message recording. `src/business-logic/CallService.js` validates direct-call eligibility, microphone-only capture, ICE configuration, and call-history mapping; `src/context/CallSessionContext.jsx` owns the single active WebRTC session and its cleanup/reconnection/minimization state machine.
- Data access: `src/data-access/supabaseMessagingRepository.js` is the production adapter for PostgREST RPC, Realtime, and private Storage signed URLs. `supabaseFriendshipRepository.js` owns friendship RPCs and Realtime while allowing pre-`079` Ride messaging to fall back to its existing schema. `src/data-access/supabaseCallRepository.js` owns call RPCs, call-row Realtime changes, and the private Broadcast signalling channel. `src/data-access/supabaseNotificationRepository.js` is the shared recipient-notification adapter, not a Module 3-specific inbox.
- Translation backend: `supabase/functions/m3-message-translation/index.ts` accepts only a message ID and target language, re-verifies authentication and current conversation visibility, reads private message content server-side, and calls Cloudflare Workers AI. Browser code never receives the Cloudflare token or supplies arbitrary source content/URLs.
- TURN backend: `m3-turn-credentials` re-verifies the authenticated participant and active call before issuing a temporary relay credential; `m3-turn-usage-monitor` reads Cloudflare egress every five minutes, fails closed after 15 minutes without a successful check, and revokes active credentials at 900 GB.
- Database: `database/sql/016_m3_supabase_messaging.sql`; `017_m3_advisor_followup.sql` covers the direct-user foreign key; `018_m3_versioned_media_paths.sql` finalizes sender/conversation/message/version object paths; `025_m3_add_voice_messages.sql` adds private standalone audio attachments and their duration contract; `026_m3_add_wav_voice_fallback.sql` adds the playback-safe WAV fallback; `033_project_notifications.sql` extends `send_message` so every other active conversation member receives a Web Push notification record; deployed `036_m3_message_translation.sql` adds the member-readable, Edge-Function-written shared translation cache; live `043_m3_add_voice_calls.sql` adds participant-only call invitations/RPCs and private Broadcast authorization without storing call audio; live `044_m3_turn_guard.sql` adds server-only relay usage and credential metadata; deployed `045_m3_reliable_voice_call_delivery.sql` adds the private incoming-call notification trigger; deployed `065_m3_terminal_chat_and_call_history.sql` is superseded by authored `075_m3_conversation_lifecycle_redesign.sql` for the redesigned personal controls, cancellation retention, notification mute, and RLS visibility; `077_m3_voice_call_presence_recovery.sql` adds device-bound presence and orphan cleanup; deployed `079_m3_friendships_and_persistent_chat.sql` adds the separate friendship/persistent-chat scope and accepted-friend write gate without changing Ride chat IDs or retention; deployed Supabase migration `20260905093400_m3_friend_ride_invitations` adds live-state Ride cards in accepted Friend chats; deployed `080_m3_group_voice_calls.sql` adds per-member call state, group invitation notifications, private signalling authorization, and independent answer/reject/leave behavior; deployed `081_m3_selective_group_voice_calls.sql` restricts each group call to the caller's selected active members.
- The previous `localMessagingStore.js` and dummy message data are legacy-only and are no longer imported by the production Module 3 path.

## Security Boundary

After deployed `065`, call-history SELECT requires both call participation and current `private.conversation_is_visible`, so traveller leave and retention expiry remove retained call-history access.

Clients receive SELECT-only grants on messaging, translation-cache, call-session, and friendship tables. Friendship changes, like message/call mutations, use narrow authenticated `SECURITY DEFINER` RPCs with empty search paths, `auth.uid()` checks, normalized-pair locks, and validated state transitions. Friend messages/media/calls share one database write gate requiring an accepted friendship and two active profiles; removal ends active calls but retains read access. Realtime call topics are private and authorize both Broadcast read and write against the active call's two participants. TURN guard/issuance tables have RLS enabled but no browser policy or grant; only server credentials can access them, and long-lived Cloudflare secrets never enter Postgres or Vite. Translation-cache writes use the Edge Runtime's server credential only after a separately authenticated user, active membership, message tombstone, and conversation-expiry check. The `message-media` bucket is private: uploads are owner/conversation staged, listing is blocked, and downloads require a current visible attachment row or the same verified Edge Function boundary.

Voice-call SQL `043`-`045`, `065`, the live `077` schema, and tracked `080`-`081`, both TURN Edge Functions, the notification Edge Function, Cloudflare secrets, and the five-minute guard are live. The frontend still requires an HTTPS release with microphone permission and three-device group validation. The shared in-app/Web Push notification integration is deployed in `033`; closed-app call alerts require the recipient to enable device notifications. Direct and group cross-browser call acceptance plus physical-device camera/microphone/translation/friendship checks remain required before a release sign-off.
