# Module 6 實機檢查清單

更新日期：2026-09-12

這份清單只包含必須由真人在實際部署環境、真實手機或真實外部服務上完成的檢查。本地 fixture、單元測試、錯誤注入、production build、架構檢查及四種自動化視窗測試已由開發端完成，不需要重複執行。

照片按鈕及照片計費提示不在本輪檢查範圍。不要測試或修改 AI 預算功能。

## 一、開始前準備

準備以下項目：

1. 已部署的最新網站網址。
2. 一部真實手機，建議使用你 presentation 當天會使用的裝置。
3. 一台桌面或筆電，用於 presentation 畫面確認。
4. 一個普通測試帳號。
5. 如要驗證帳號隔離，再準備第二個測試帳號。
6. 手機定位和麥克風權限一開始設為「詢問」。
7. 開啟 Supabase Edge Function 日誌，以便 AI 出錯時查找相同時間的紀錄。

每次發現問題，立即保存：

- 畫面截圖；
- 當時完整網址；
- 發生時間；
- 使用的手機、瀏覽器和帳號；
- AI 回覆中的 `traceId`，如畫面或網路回應有提供；
- Supabase 對應時間的錯誤日誌。

## 二、手機首頁與真實定位

### 1. 訪客首次進入

1. 使用手機無痕模式開啟網站。
2. 不登入，進入 Explore／Home。
3. 查看標題上方的小字和出發地摘要。

應看到：

- 訪客顯示 `Starting from Kuala Lumpur`，或目前已確認的出發地；
- Kuala Lumpur 被清楚標示為預設起點；
- 頁面沒有聲稱這就是手機目前位置；
- 卡片、篩選和底部導航沒有重疊。

### 2. 手動更改出發地

1. 點擊出發地摘要。
2. 手動搜尋你現在所在的城市、酒店或附近明確地點。
3. 從建議清單選擇正確結果。
4. 記下任意一張景點卡片的距離。
5. 打開該景點詳情。

應看到：

- 首頁顯示新起點；
- 詳情頁使用同一個起點；
- 首頁和詳情距離一致；
- 距離被描述為直線距離，不是車程或道路距離；
- 精確座標沒有出現在網址中。

### 3. 允許真實定位

1. 再次打開出發地設定。
2. 點擊 `Use my location`。
3. 手機詢問權限時選擇允許。
4. 等待定位完成。

應看到：

- 顯示真實可理解的地址或地點名稱；
- 不應只顯示 `Current location`；
- 載入完成後按鈕不會永久停留在定位中；
- 新起點會重新計算推薦和距離。

### 4. 拒絕定位

1. 在手機設定中移除網站定位權限，或重新使用無痕模式。
2. 點擊 `Use my location`。
3. 選擇拒絕。

應看到：

- 原本的出發地不會消失；
- 顯示清楚的失敗訊息；
- 仍可手動搜尋出發地；
- 不影響繼續瀏覽景點。

### 5. 分頁保存範圍

1. 在同一分頁設定一個新起點並重新整理。
2. 確認起點仍存在。
3. 開啟新的無痕分頁，直接貼上相同 Home 網址。

應看到：

- 同一分頁重新整理後保留起點；
- 新分頁沒有舊分頁的精確位置資料；
- 新分頁回到清楚標示的預設起點。

## 三、真實景點、日期與篩選

### 1. 日期不會自行改變

1. 選擇一個確定沒有共乘行程的未來日期。
2. 記下日期。
3. 切換分類、搜尋景點並進入詳情。
4. 返回 Explore。

應看到：

- 日期始終保持不變；
- 系統不能因為其他日期有車而自動改日期；
- 如果顯示替代日期，只有你點擊後日期才會改變。

### 2. 搜尋和分類一致性

1. 分別選擇 Nature、Culinary、Heritage 和 Event。
2. 每次查看所有結果區域。
3. 輸入一個景點名稱，再輸入一個州屬名稱。
4. 輸入一個不存在的文字。

應看到：

- 所有結果區域都遵守相同分類和搜尋文字；
- 不會使用不符合條件的景點補滿畫面；
- 沒有結果時顯示清除條件操作；
- 日期、分類和搜尋文字保存在網址中；
- 選回 All 後恢復一般推薦，不會把本次分類偷偷存成長期偏好。

### 3. 真實資料抽查

至少抽查：

- 三個不同州屬；
- 四種分類各一個景點；
- 一個很長的景點名稱；
- 一個中文或其他非拉丁字母名稱；
- 一個沒有行程的景點；
- 一個確實有已列行程的景點。

應看到：

- 官方名稱、州屬和分類合理；
- 不應出現 Brunei、Thailand 或其他馬來西亞以外地點；
- 已退役景點不應被推薦；
- 缺少的營業時間、價格、交通或人流資料不會被猜測補上。

## 四、真實交通狀態與找車交接

### 1. 有行程並有座位

找到一個部署資料中確實有行程和座位的景點及日期。

應看到：

- 顯示已列行程數量；
- 座位寫成「某一個已列行程最多有多少座位」；
- 顯示需要確認上車點、時間和剩餘座位；
- 不應說旅客一定能搭乘或一定能到達上車點。

### 2. 有行程但沒有座位

找到一個已滿座的行程，或使用專用測試行程將剩餘座位設為零。

應看到：

- 仍顯示有已列行程；
- 顯示 `No seats remaining`；
- 不能錯誤顯示成沒有行程。

### 3. 沒有行程但有瀏覽興趣

使用兩個測試帳號，在同一日期打開同一個沒有行程的景點。

應看到：

- 交通狀態顯示該日期沒有已列行程；
- 瀏覽興趣另外顯示；
- 興趣不能代替交通狀態；
- 文案不能把瀏覽興趣說成承諾出行、預訂或即時人流。

### 4. Find a ride 交接

1. 在景點詳情找到 `Find a ride`。
2. 點擊前確認上方可看到 10 公里提示。
3. 點擊進入 Search。
4. 檢查日期、目的地和 Pickup 欄位。

應看到：

- 提示為搜尋可能包含終點在景點 10 公里內的行程；
- Search 保留景點和日期；
- 網址保留 `proximityKm=10`；
- Pickup 保持空白；
- 系統沒有把旅客的住宿地點當成已確認上車點；
- 沒有搜尋結果時不會移除日期或自動擴大條件。

### 5. I will drive 交接

在沒有行程的景點點擊 `I will drive`。

應看到：

- 進入發布行程流程；
- 目的地和日期保留；
- 不會自動發布；
- 上車點仍需要在 Module 2 中確認。

## 五、真實通知與登入保存

### 1. 訪客登入返回

1. 登出後打開一個未來日期的景點。
2. 點擊 `Tell me when there is a ride`。
3. 完成登入。

應看到：

- 登入頁解釋登入原因；
- 返回同一景點和同一日期；
- 不會在登入後自動登記通知；
- 需要再次由使用者確認操作。

### 2. 登記、重新整理及取消

1. 登入後登記通知。
2. 重新整理詳情頁。
3. 登出再登入。
4. 返回同一景點和日期。
5. 取消通知並再次重新整理。

應看到：

- 登記後顯示已啟用狀態；
- 重新整理和重新登入後仍存在；
- 重複點擊不會產生多筆活動通知；
- 取消後狀態正確保存；
- 文案說明通知不是預訂，也不保證會有司機。

### 3. 第二帳號隔離

使用另一個測試帳號打開相同景點。

應看到：

- 第二個帳號看不到第一個帳號的個人通知狀態；
- 公開畫面最多顯示匿名聚合興趣數，不顯示個人身份；
- Past Plans、興趣及通知不能跨帳號讀取。

## 六、真實 Tumpang Guide

每一輪 AI 測試都記下發送時間、完整輸入、完整回覆和 `traceId`。

### 1. 正常推薦

在 Travel Brief 設定：

- 出發地：你目前所在的真實地點；
- 日期：一個未來日期；
- 人數：2；
- 分類：Nature。

發送：

`Plan a nature day for us.`

應看到：

- 一至三張資料庫景點卡片；
- 開場只是一句簡短總結，不重複逐一描述景點；
- 卡片 Place ID 對應真實資料庫景點；
- 評論數不被解讀為安靜或擁擠；
- 直線距離不被說成道路時間或容易到達；
- 已列行程不被描述為一定適合旅客。

### 2. 模糊需求及預算回歸

開新聊天，依序發送：

1. `saya nak makan`
2. 回答它詢問的出發地，例如 `Kuala Lumpur`
3. `kamu suggest me lah, i no idea`

應看到：

- 每次只詢問一個真正缺少的必要條件；
- 不出現內部指令文字；
- 不詢問預算；
- 還沒有推薦卡片時，不會聲稱已完成推薦。

### 3. 具體景點資訊

對一個剛剛推薦的景點依序詢問：

1. `What should I know about this place?`
2. `What time does it open?`

應看到：

- 使用正確的上下文景點；
- 具體資料以聊天文字顯示，不再建立推薦卡片；
- 有可信營業時間時提供來源；
- 查不到時明確說無法取得；
- 不能用一般景點描述冒充營業時間答案。

### 4. 景點詳情交接

1. 在景點詳情點擊 `Ask Tumpang Guide`。
2. 查看帶入的景點名稱和問題草稿。
3. 先不要按發送。
4. 選擇使用該問題，再自行修改後發送。
5. 返回景點。

應看到：

- 進入 Guide 時不會自動呼叫 AI；
- 問題綁定正確景點，不是只根據名稱猜測；
- 日期和出發地保留；
- 返回後仍是原本景點和探索條件。

### 5. 原草稿保留

1. 先在 Guide 輸入一段文字但不要發送。
2. 返回景點詳情，再次進入 Guide。
3. 分別測試 `保留原草稿` 和 `使用此問題`。

應看到：

- 兩個選擇都清楚可見；
- 不會靜默刪除原文字；
- 不會自動發送任何內容；
- 英文、簡中、馬來文和淡米爾文都能顯示相應交接文案。

### 6. 四種核心語言

各開一個新聊天並發送：

1. `I want a nature place in Penang.`
2. `我想在槟城找一个自然景点。`
3. `Saya mahu tempat alam semula jadi di Pulau Pinang.`
4. `பினாங்கில் இயற்கை இடம் வேண்டும்.`

應看到：

- 回覆語言跟隨當前訊息；
- 官方景點名稱不被錯誤翻譯；
- 四種語言都不使用評論數推論人流；
- 四種語言都正確描述座位、直線距離、瀏覽興趣和所選日期無行程。

### 7. Gemini 與 Groq 接替

1. 先完成一次正常 AI 回覆。
2. 在可控制的測試部署中讓 Gemini 暫時不可用。
3. 發送一個新的、可清楚辨認的問題。
4. 檢查 Edge Function 日誌。
5. 再測試兩個 provider 都不可用的情況。

應看到：

- Gemini 失敗後由 Groq 從同一輪原始狀態完整處理；
- 不會混合 Gemini 的半段結果和 Groq 的半段結果；
- 同一個 `clientTurnId` 不重複執行成功寫入；
- 兩者都失敗時保留聊天和 Travel Brief，並提供重試；
- 429 或 timeout 被顯示為服務問題，不是使用者的對話次數用完。

如果無法安全控制 provider 故障，將這項標為「未驗證」，不要在 presentation 中聲稱 fallback 已經實機證明。

### 8. 真實手機語音

對英文、中文、馬來文和淡米爾文各測試一次：

1. 選擇語音語言。
2. 點擊麥克風並允許權限。
3. 說出一句完整需求。
4. 停止錄音。
5. 修改辨識文字。
6. 手動按發送。

應看到：

- 辨識結果只填入輸入框，不自動發送；
- 修改後文字不會被舊結果覆蓋；
- 拒絕麥克風權限後能正常停止並顯示錯誤；
- 瀏覽器辨識失敗時，Groq 雲端轉錄必須由使用者手動選擇；
- 雲端轉錄會重新錄音，不會偷偷上傳之前的音訊。

## 七、真實錯誤恢復

在不修改正式資料的前提下，使用手機切換飛行模式或關閉網路進行以下檢查：

1. 景點列表載入期間斷網。
2. 景點詳情載入期間斷網。
3. 登記通知時斷網。
4. Guide 送出訊息後斷網。
5. 恢復網路後使用畫面提供的重試。

應看到：

- 載入最終進入成功或失敗狀態，不會永久轉圈；
- 景點失敗不會說成沒有景點；
- 行程失敗不會說成沒有行程；
- 通知失敗保留原狀態，不顯示假成功；
- AI 失敗保留原聊天和 Travel Brief；
- 網路恢復後可以正常重試。

## 八、手機與 presentation 裝置排版

在真實手機和 presentation 電腦上都完成：

1. Explore 首頁從頂部捲到最底。
2. 打開出發地對話框並叫出手機鍵盤。
3. 打開長名稱景點詳情。
4. 展開評分。
5. 打開 Guide onboarding、Travel Brief 和推薦卡片。
6. 打開通知或儲存確認對話框。
7. 將手機旋轉一次。
8. 在 presentation 電腦將瀏覽器縮放到 125% 和 200%。

應看到：

- 頂部與底部導航不遮住內容；
- 對話框可以完整捲動；
- 鍵盤不會永久遮住輸入框和發送按鈕；
- 長名稱正常換行；
- 沒有按鈕互相重疊；
- 旋轉和縮放後不丟失日期、起點、篩選或草稿；
- 鍵盤焦點可見，Escape 關閉桌面對話框後焦點回到原按鈕。

## 九、presentation 前最後五分鐘檢查

1. 使用乾淨測試帳號登入。
2. 確認 Home 顯示會員名字和正確起點。
3. 確認一個有行程景點、一個無行程景點確實存在。
4. 確認通知按鈕可用且沒有殘留舊狀態。
5. 發送一條最短 AI 測試訊息並確認 provider 正常。
6. 準備一個已載入的 fixture／截圖備援畫面，避免現場網路或 AI 故障導致無法展示。
7. 不清除或修改正式景點資料，不在 presentation 當場部署新程式。

## 十、回報格式

每個問題使用以下格式回報：

```text
測試項目：
測試時間：
裝置／瀏覽器：
帳號：訪客／測試帳號
開始網址：
操作步驟：
預期結果：
實際結果：
是否可重現：每次／偶爾／一次
traceId（AI 問題）：
Supabase 日誌：
截圖或錄影：
```

優先回報：錯誤推薦、錯誤交通狀態、日期或起點丟失、通知假成功、AI 自動送出、帳號資料互相可見，以及任何無法恢復的永久載入。
